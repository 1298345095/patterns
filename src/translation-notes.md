## 怎样区分原文与补充

普通正文是原文的中文翻译，尽量保留原有论述顺序、例子、论证强度与取舍，
同时调整语序以符合中文表达。原作者提出的建议仍以原作者的立场呈现，
不因为译者赞同或反对而改写结论。

补充内容使用就近的引用块，并明确标记：

- **译注（学习提示）**：解释原文隐含的前提、类型或所有权约束、设计取舍，
  帮助已有 Rust 基础的读者继续深入。
- **译注（原文疑点）**：指出原文含糊、不完整、与示例不一致或疑似有误的地方。
  原句的译文或原代码仍保留，注解说明问题出在哪里。
- **译注（版本说明）**：区分历史背景、特定工具链版本与现在的阅读语境。
  原文中“未来会支持”等表达不代表译者对 Rust 路线图作出承诺。

2026 年的 stable 补充也会以带年份或版本号的译注、独立小节出现；
这些内容是译者的技术审校，不属于原作者历史论述。

原书有些短页或小节本来就未展开，例如“重构”中的“小步修改”。
译本保留这种状态并明确说明，不以译者撰写的新正文填补原书空缺。

代码中的自然语言注释译成中文；标识符、类型名、字符串字面量、命令和原始错误输出
原则上保持原样，便于复现和对照。`ignore`、`compile_fail`、隐藏的 `#` 行等
代码块约定也予以保留。代码本身若存在问题，会在相邻译注中解释，
不会为了让示例通过测试而悄悄改成另一个实现。

因此，“原书代码被保留”不等于“每个代码块都可以直接复制运行”。
有的例子是片段，有的故意展示编译错误，有的依赖外部库，有的保留了原书的实际缺陷。
阅读时应同时查看代码块说明和译注。

原有参考链接保留，中文化的是显示文字。章节文件沿用原有路径，
目录中的标题相应译为中文。原书外链中可能有旧分支名、历史文章或已迁移的地址；
保留链接不表示已经逐一保证外部页面当前可用。

## 主要术语

| 英文                        | 本书用语                          | 阅读时要区分的含义                                            |
| --------------------------- | --------------------------------- | ------------------------------------------------------------- |
| idiom                       | 惯用法                            | 社区常见且自然的写法，不是不可违背的语言规则                  |
| design pattern              | 设计模式                          | 针对一类重复问题的结构与取舍                                  |
| anti-pattern                | 反模式                            | 看似能解决问题，却经常引入更大代价的做法                      |
| trait / trait bound         | trait / trait 约束                | 保留关键字，避免与其他语言的接口概念直接等同                  |
| ownership / borrow          | 所有权 / 借用                     | 数据归谁负责，与谁暂时可以访问是不同问题                      |
| shared / mutable reference  | 共享引用 / 可变引用               | 原文写 immutable 时也可能译为不可变引用；注意内部可变性       |
| coercion                    | 强制转换                          | 编译器在特定位置进行的隐式类型转换，区别于显式 `as` 转换      |
| dereference                 | 解引用                            | 区分指针访问、自动解引用和借助 `Deref` 公开的方法             |
| static / dynamic dispatch   | 静态分发 / 动态分发               | 调用目标如何确定，与对象是否放在堆上并非同一问题              |
| monomorphization            | 单态化                            | 泛型代码针对具体类型生成对应实现                              |
| newtype                     | 新类型（newtype）                 | 用包装结构体建立独立类型，而非类型别名                        |
| wrapper                     | 包装器 / 包装类型                 | 封装底层表示或额外约束的类型                                  |
| interior mutability         | 内部可变性                        | 在共享访问下管理变化的机制，不意味着绕开一切借用约束          |
| invariant                   | 不变量                            | 对某个抽象的有效状态始终应成立的条件                          |
| RAII guard                  | RAII 守卫                         | 用拥有所有权的值管理资源与清理时机                            |
| FFI / ABI                   | 外部函数接口 / 应用程序二进制接口 | API 语义、内存布局和调用约定应分别考虑                        |
| unsafe / undefined behavior | 不安全操作 / 未定义行为           | `unsafe` 是承担额外证明义务的位置，未定义行为是违反约束的后果 |
| sum / product type          | 和类型 / 积类型                   | 前者表达多选一的变体，后者组合多个分量                        |
| type class                  | 类型类                            | 来自 Haskell 等语言的概念，与 Rust trait 的对应有边界         |
| optics / lens / prism       | 光学抽象 / 透镜 / 棱镜            | 保留 optics 等英文词，帮助辨认组合式的数据访问抽象            |
| fold                        | 折叠                              | 既可能指迭代归约，也可能指重建递归数据结构，须按上下文理解    |
| zero-cost abstraction       | 零成本抽象                        | 不应理解为“任何使用方式都没有运行时工作”                      |

## 面向已有基础的阅读方法

读每个模式时，可以依次追问以下四件事：

1. **模式守住了什么条件？**
   是资源只释放一次、类型不能混用，还是某种状态不可构造？
2. **条件由谁保证？** 是编译器、类型的公开接口、运行时检查，还是 FFI
   调用者的承诺？
3. **变化发生在哪里？** 添加新操作、新数据类型或新的后端时，需要修改哪些模块？
4. **成本落在哪里？** 除了运行时间，还要考虑分配、代码体积、编译时间、API
   稳定性， 以及调用者理解契约的负担。

例如，读 Builder 时不只看链式调用，还可以比较消费 `self` 与借用 `&mut self`
如何影响复用与构造状态；读 Visitor 和 Fold 时，可以追踪遍历是否修改原树、
是否保留共享节点；读 FFI 时，应逐个指出指针的来源、有效期、释放方和重入限制。
这些问题对应正文中的学习提示，也有助于判断一个模式是否适合自己的代码。
